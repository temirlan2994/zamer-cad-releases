# Стены v2: самостоятельные стены, помещения из петель, редактирование в 3D (проект, 2026-11-06)

Статус: архитектурный проект, код не менялся. Продолжает
`docs/walls-geometry-design.md` (далее — «геометрическая схема»): там описан движок
`deriveWallsV2` для стен, выведенных из комнат («стена = область»). Здесь — как в
тот же движок встают **ручные стены** (как в Revit/ArchiCAD), как из замкнутых
петель стен получаются **помещения**, как стены редактируются **в 3D**, и как всё
это ложится на схему `kepler-plan/6`.

Неизменное условие: блок-комнаты (`level.rooms[]`, из которых сейчас выводит стены
`core/walls.js → deriveWalls`) остаются и остаются основным способом планировки.
Ручные стены — второй источник стен, а не замена.

---

## 0. Ключевые решения (кратко)

1. **Два источника — один движок.** Стена в результате `deriveWallsV2` — запись с
   `source: 'room' | 'manual'`. Стены комнат по-прежнему *выводятся* (не
   хранятся); ручные стены *хранятся* в новом массиве `level.walls[]`. Обе
   превращаются в прямоугольники и объединяются в одну область `W` на одной сжатой
   сетке — узлы Т/углы/ступени между ручной стеной и стеной комнаты получаются
   так же, как между двумя комнатами, без `joint`/`chamfer`.
2. **Параметры стены комнаты** (высота, тип, слои, привязка верха) хранятся, как
   сейчас толщина, в `level.wallOverrides[key]` — ключи `e|room|side`,
   `s|idA|idB` уже есть (`ownKey`/`sharedKey` в `core/walls.js`). Отдельного
   объекта стены для комнаты не заводим: иначе две истины (контур комнаты и
   объект стены) будут расходиться при каждом перетаскивании.
3. **«Отвязать стены»** — явная команда: стены блок-комнаты становятся ручными
   (`source: 'manual'`), комната становится помещением «по стенам». Обратного
   автоматического пути нет (только отмена).
4. **Помещение из петли** — новый вид комнаты `room.bound = { mode: 'walls', seed }`.
   Контур не хранится как истина: он вычисляется как связная компонента
   дополнения `W` (заливка клеток той же сжатой сетки), содержащая `seed`.
   Планарный граф осей не нужен, пока стены ортогональны.
5. **Перекрывающиеся блок-комнаты** — ошибка планировки (подсветка в нормах), стены
   внутри чужого `P_s` не рисуются; старого «covered → перегородка» нет. Нужна
   перегородка — рисуется ручной стеной. В реальном проекте
   `tests/fixtures/user-house-2026-11.json` перекрытий 0 (проверено 2026-11-06),
   в шаблонах — проверить на этапе 2.
6. **Ось ручной стены** хранится общо (отрезок или дуга), но движок v2 на первых
   этапах принимает только ортогональные отрезки в осях дома; косые и дуговые —
   отдельный этап с вендоренным полигональным отсечением (раздел 6, этап F).
7. **3D-редактирование** — выбор лучом по осевым параллелепипедам (CPU, без
   ID-буфера, работает и в canvas-2D-запасном режиме `ui/view3d.js`), ручки на
   грани, запись в модель теми же функциями, что и план (`core/wall-edit.js`,
   `core/wall-thickness.js`, новый `core/wall-manual.js`).
8. **Схема 6** добавляет только новые необязательные поля: `level.walls[]`,
   `room.bound`, `opening.host`, `project.wallTypes[]`. Миграция 5→6 — добавить
   пустой `walls: []` на каждый этаж (и в этажи вариантов); геометрия не меняется.

## 1. Модель объекта стены

### 1.1. Хранимая ручная стена (`level.walls[]`, только `source: 'manual'`)

```js
{
  id: 'wall-…',                 // makeId('wall')
  axis: {                        // в осях дома, мм, Y вниз
    kind: 'line',                // 'line' | 'arc' (arc — этап F)
    a: { x, y }, b: { x, y },
    // arc: { cx, cy, r, a0, a1, ccw } — зарезервировано
  },
  justify: 'center',             // линия привязки: 'center' | 'left' | 'right'
                                 // (лево/право — по направлению a→b), как Location Line в Revit
  thickness: 200,                // мм; если есть typeId — сумма слоёв типа
  typeId: null,                  // ссылка на project.wallTypes[] (этап E)
  wallType: 'partition',         // класс: 'exterior' | 'bearing' | 'partition' (как сейчас)
  base: { offset: 0 },           // низ = level.elevation + offset
  top: { level: null, offset: 0, height: null },
                                 // top.level = id этажа → верх = его elevation + offset
                                 // иначе height ?? (level.height − плита), как roomCeiling в model.js
  hidden: false,                 // «линия разделения»: не рисуется, но участвует в W и в поиске помещений
  roomBounding: true,            // ограничивает помещения (Room Bounding в Revit)
}
```

Привязка к этажу — массивом: стена лежит в `levels[i].walls`, как комнаты и
мебель; `project.walls` — проекция активного этажа (добавить `'walls'` в
`LEVEL_KEYS` в `core/model.js`). Стена через несколько этажей — это `top.level`
выше своего; на плане верхних этажей она показывается как «стена снизу» (как
сейчас `belowWalls` в `ui/store.js`), а не дублируется.

### 1.2. Стена комнаты (выводится, не хранится)

Как сейчас: сегменты рёбер `roomBoundaryEdges` (`core/room-shape.js`), ключи
`ownKey(room, side)` / `sharedKey(a, b)`. Хранимые параметры — только в
`wallOverrides[key]`: сейчас `{ thickness, kind }`; добавляются необязательные
`base`, `top`, `typeId`, `hidden` (часть уже есть). Чтение — одной функцией
`wallParams(project, key)` в `core/walls-v2.js`, чтобы ручные и комнатные стены
давали потребителям одинаковые поля.

Слабое место — стабильность ключа у контурных комнат (`room.outline`): при
вставке вершины (`splitRoomOutlineWall`) номера сторон сдвигаются, и override
«переезжает». Это существует и сейчас; в v2 при правке контура переписывать ключи
`wallOverrides` в том же действии (функция `remapOutlineKeys` рядом с
`finalizeRoomOutline`). Тест — в этапе B.

### 1.3. Выходная запись `deriveWallsV2`

Контракт геометрической схемы (раздел 4) плюс:

| Поле | Комнатная | Ручная |
|---|---|---|
| `source` | `'room'` | `'manual'` |
| `key` | `e|…` / `s|…` | `m|<id>` |
| `rooms` | id комнат по сторонам | id помещений по сторонам (из поиска петель, раздел 2), может быть пустым |
| `edge`, `outward`, `sides` | как сейчас | `edge` = отрезок грани привязки; `outward` — нормаль «влево»; `sides` = [] |
| `from`/`to`, `center`, `orient`, `thickness`, `wallType`, `hidden` | как сейчас | из объекта |
| `band` | выдавливание без удлинения | прямоугольник ось±толщина без торцов |
| `rects`, `polys` | куски области после атрибуции | то же |
| `z0`, `z1` | из level + overrides | из `base`/`top` |
| `wallId` | — | `id` объекта |

`wall-edit.js`, `wall-thickness.js`, `plan-actions.js` ветвятся по `source`:
комнатная стена правится через контуры комнат (как сейчас `moveWallBy`), ручная —
через объект (раздел 1.5).

### 1.4. Единый движок: как ручная стена встаёт в `W`

Шаги геометрической схемы (раздел 3) расширяются:

1. **Сегменты.** К сегментам рёбер комнат добавляются ручные стены: прямоугольник
   `band` по оси, толщине и `justify`. Торцы ручной стены продлеваются на
   половину толщины соседа, если торец лежит на чужой стене или ближе 1 мм к её
   грани/оси (притягивание узла) — иначе остаётся щель-волосок. Продление
   режется по `W` соседа, лишнего не появляется (объединение).
2. **Вычитание чужих помещений.** Кольца комнат вычитают чужие `P_s` (как в
   схеме). **Ручные стены не вычитаются** — пользователь сам нарисовал стену там,
   где она есть. Если ручная стена проходит через блок-комнату, это не дефект
   движка, а событие модели: нормы показывают «Стена делит помещение «Гостиная»»
   с действием «Разделить на два» (раздел 2.5). Инвариант c в
   `tests/wall-invariants-lib.mjs` получает исключение для `source: 'manual'`.
3. **Атрибуция клетки** (кому принадлежит угол/узел): к правилам схемы перед
   «ближе по нормали» добавляется: при равной близости `manual` > `shared` >
   `own`; при пересечении ручной стены с комнатной на всю толщину (крест) — клетки
   креста отдаются более толстой, при равенстве — ручной. Правило фиксируется
   тестом-фикстурой `manualCrossesRoomWall`.
4. **Выход** — без изменений: `rects`/`polys` по ключу, `wallOutline(walls)` —
   единый контур для штриха и DXF.

Итог: одна функция `deriveWallsV2(project)` в `core/walls-v2.js`, источники —
`rooms` + `walls` этажа; потребители не знают, откуда стена.

### 1.5. Правка ручной стены (`core/wall-manual.js`, новый)

- `createWall(axis, opts)`, `moveManualWall(project, id, delta)` (сдвиг по
  нормали), `dragManualWallEnd(project, id, end, point, snap)`,
  `setManualWallThickness` (с сохранением грани привязки, как
  `stretchRoomShape`), `setWallHeight(project, key, {base, top})` — общая для
  обоих источников (для комнатной пишет в `wallOverrides`).
- **Связность узлов.** Revit двигает присоединённые стены вместе. Здесь —
  легко: в начале перетаскивания собрать стены, чьи торцы лежат на оси/грани
  двигаемой (допуск 1 мм), и продлевать/укорачивать их торцы до новой линии.
  Хранить «соединения» в модели не нужно — они вычисляются из геометрии.
- Проёмы на ручной стене (раздел 1.6) пересчитывают `t`, чтобы остаться на
  месте в мире (как `captureOpeningAnchors` в `wall-edit.js`).

### 1.6. Проёмы-хосты

Сейчас проём привязан к комнате: `{ roomId, side, offset }` (`createOpening` в
`core/model.js`; `side` 0–3, у контурных комнат — индекс ребра).
В v6 добавляется необязательное `host`:

```js
opening.host = { wallId: 'wall-…', t: 1250 }   // t — центр проёма от axis.a, мм
```

- Проём на ручной стене: `host` задан, `roomId` = помещение со стороны
  открывания (для `swingIn`), может быть `null`.
- Проём на комнатной стене: как сейчас, `host` нет.
- Единый резолвер `resolveOpeningWall(project, opening, walls)` в
  `core/walls-v2.js`; `openingRect`, `doorSymbol`, `doorSwingRect`, `doorLink`,
  `clampOpeningOffset`, `wallAt` вызывают его вместо поиска по `roomId/side`.
- «Отвязать стены» переводит проёмы комнаты в `host` той же мировой позиции.
- Удаление ручной стены удаляет её проёмы (как `removeRoom` удаляет проёмы
  комнаты), с отменой.

### 1.7. Типы и слои (этап E)

`project.wallTypes[] = { id, name, wallType, layers: [{ name, material, thickness, core: bool }] }`.
`thickness` стены = сумма слоёв. Слои нужны IFC (`IfcMaterialLayerSetUsage` в
`core/ifc.js`), разрезу (`ui/render-section.js`) и спецификации; на плане —
штриховка ядра. Хранить слои в каждой стене не нужно — только `typeId`.
Сейчас классы толщин живут в `settings` (`wallClassThickness`,
`setWallDefaults`) — они становятся тремя встроенными типами по умолчанию.

## 2. Помещение из петли стен

### 2.1. Два вида комнат

| | Блок-комната (есть) | Помещение по стенам (новое) |
|---|---|---|
| Истина | `x,y,w,h` / `notch` / `outline` | стены вокруг + `seed` |
| Стены | порождает (кольцо) | не порождает |
| Поле | — | `room.bound = { mode: 'walls', seed: {x,y} }` |
| Контур | `roomPolygon(room)` | кеш `room.poly` (вычисляется, хранится только для отмены и экспорта) |
| Перетаскивание | двигает комнату и её стены | двигаются стены, контур следует |

Всё, что читает комнату (нормы, ТЭП, площади, подписи, мебель, инсоляция,
IfcSpace), работает через `roomPolygon`/`roomRects`/`roomContainsPoint`
(`core/room-shape.js`). Эти функции получают ветку: для `bound` они возвращают
кешированный `room.poly`. Кеш обновляется в одной точке — после `deriveWallsV2`
(в `ui/store.js`, где сейчас кешируются `walls`) функцией
`resolveBoundRooms(project, walls)`. Так ни один потребитель не меняется.

### 2.2. Поиск замкнутых контуров

Решение: **заливка дополнения `W` на сжатой сетке**, а не грани планарного графа
осей.

1. Сетка уже построена движком (`core/ortho-grid.js`, этап 1 схемы). Клетки вне
   `W` и вне блок-комнат — «свободные». Стены с `roomBounding: false` в `W` для
   этой заливки не входят; `hidden`-стены (линии разделения) — входят.
2. Связные компоненты свободных клеток (4-связность, BFS по индексам). Компонента,
   касающаяся края сетки, — улица. Остальные — замкнутые петли.
3. Контур компоненты — обход границы клеток (та же функция, что `polys` стен):
   внешний цикл + дыры (колонна-стена внутри помещения). Это сразу **чистый**
   контур — площадь «в свету», как у блок-комнат.
4. Минимальный размер петли — `MIN_SHAFT_SIZE` (200) по обеим осям, иначе это
   щель, а не помещение.

Почему не граф: у нас стены с толщиной и узлами из объединения; граф осей
требует допусков на «почти касание», отдельной логики Т-узлов и разной толщины,
и всё равно потом надо отсекать толщину. Заливка по сетке использует ровно ту
геометрию, что рисуется, — помещение не может разойтись со стенами. Сложность
O(Nx·Ny), те же < 5 мс. Граф (DCEL с полуребрами) понадобится только с косыми
стенами (этап F), и тогда грани берутся из того же полигонального объединения.

### 2.3. Связь помещение ↔ стены

- Помещение ↔ петля: компонента, содержащая `room.bound.seed`.
- Стены помещения: ключи стен, чьи клетки граничат с компонентой — в
  `wall.rooms` выходной записи (для ручных) и в `room.boundWalls` (не хранится,
  считается). Это нужно для `analyzeConnectivity` (`core/rooms.js`, двери между
  помещениями), `doorLink`, норм.

### 2.4. Что происходит при перетаскивании стены

На каждом кадре — `deriveWallsV2` → `resolveBoundRooms`:

1. Петля, содержащая `seed`, найдена — `room.poly` обновлён. Если `seed` попал
   в стену (стену протащили через точку), берётся компонента с максимальным
   пересечением с прошлым `room.poly`, `seed` переставляется в
   `roomLabelPoint` нового контура (запись в модель — только на `finalize`).
2. **Петля разомкнулась** (стену удалили/отодвинули, помещение «вытекло» на
   улицу): помещение остаётся с последним контуром, статус `unbounded`, в нормах —
   «Помещение не замкнуто», на плане — красный пунктир контура (как Revit «Not
   Enclosed»). Площадь в ТЭП не входит.
3. **Две петли слились** (удалена стена между ними): оба помещения в одной
   компоненте → предупреждение «Два помещения в одном контуре», площадь
   приписывается первому, второе `unbounded`. Предлагается объединить.
4. **Петля разделилась** (стена дорисована через помещение): помещение остаётся
   в части с `seed`; вторая часть — свободная петля без помещения: на плане
   штриховка «не назначено» и кнопка «Создать помещение».
5. Мебель **не двигается** вместе со стеной (мебель свободная, `createItem`); но
   при перемещении помещения целиком (выделить помещение + его стены и тянуть)
   мебель внутри едет, как сейчас с блок-комнатой.

### 2.5. Совместимость с блок-комнатами

- Блок-комната занимает свои клетки: заливка их не трогает, помещение по стенам не
  может создаться внутри блок-комнаты. Петля, образованная **кольцами блок-комнат и
  ручными стенами вместе** (например, коридор между тремя блоками, замкнутый
  одной ручной стеной), — обычное помещение по стенам. Это главный практический
  сценарий: «добить» план стенами.
- Ручная стена через блок-комнату — предупреждение + действие «Разделить на два»:
  блок-комната превращается в две блок-комнаты по линии стены (контуры через
  `polygonRects`/`outline`), ручная стена удаляется, её проёмы переходят на общую
  стену `s|a|b`. Так блок-модель остаётся главной там, где она уже есть.
- «Отвязать стены» (раздел 0, п. 3) — обратное направление: блок → помещение по
  стенам.

### 2.6. Нормы, площади, мебель

- `core/norms.js`, `core/tep.js`, `core/rooms.js → roomNetAreaM2/totalAreaM2`,
  `core/clearance.js`, `core/furnish.js`, `core/label-anchor.js`,
  `core/insolation.js` — через `roomPolygon`/`roomRects`, изменений нет, кроме
  исключения `unbounded` из площадей.
- `roomNetAreaM2` для `bound` = площадь компоненты (уже чистая; `eatersOf` —
  вложенные/шахты — не применяется, их клетки уже не в компоненте).
- `buildingFootprintM2`/`computeBuildingOutline` — объединение комнат **и** `W`
  (сейчас только комнаты + толщина): иначе дом из одних ручных стен даёт нулевое
  пятно. Тест на фикстуре «дом из ручных стен».
- Автоподбор мебели (`arrangeRoom` в `ui/store.js`) работает с `room.poly`.

### 2.7. Правка помещения по стенам «как обычного»

`core/bound-edit.js`: правка помещения транслируется в правку его ручных
стен, контур пересчитывается заливкой.
- Сторона/угол (ручки `bound-e-i`/`bound-v-i` из `roomShapeHandles`),
  ширина/глубина в свойствах (`resizeBoundRoom`: правая и нижняя стороны) →
  `moveBoundRoomEdges` → `moveManualWall` стен, чья грань лежит на стороне.
  Общая стена двигает и соседа. Сторону, которую замыкает не ручная стена
  (блок-комната, торец), не тянем — причина тостом.
- Перенос/поворот группы (`moveRoomGroup`/`rotateRoomGroup` →
  `transformBoundGroup`): стены петли (`boundLoopWalls`), seed и кеш контура;
  проёмы `host` едут сами. Стена, общая с невыбранным помещением по стенам, —
  отказ «выделите и его».
- Копия (Ctrl+D, буфер, вставка на другой этаж — на то же место):
  `captureRoomGroup` кладёт стены петли и их проёмы, `planBoundCopy` ищет
  место, проверяет пробной вставкой и даёт новые id и seed.
- После каждой правки `followBoundRooms` переставляет seed по ожидаемому
  контуру, затем проверка: помещения правки замкнуты (перенос/копия — та же
  площадь и место), бывшие замкнутыми соседи не разомкнулись; иначе откат.

## 3. 3D

### 3.1. Тело стены из той же геометрии

`core/mesh3d.js` сейчас собирает «пробеги» (`wallRuns`) из `band` по
`own/shared` + `wallJoinPatches`, режет проёмы (`cuts` по `openingRect`) и
выдавливает `wallPiece`/`boxFaces`. В v2:

1. Для каждой записи — её `rects`, каждый прямоугольник выдавливается от `z0` до
   `z1` записи (у ручных и комнатных стен с разной высотой — разные z).
2. Проёмы режутся по тем же `rects`, что пересекает `openingRect` (сейчас — по
   пробегу); логика нижней/верхней перемычки (`bottom`/`top`) остаётся.
3. Внутренние грани между соседними прямоугольниками одной высоты не
   выдавливаются: боковые грани строятся по контуру `polys` (обход границы),
   верх — по `rects`. Это убирает внутренние полигоны и z-конфликт, который сейчас
   лечит `joinedStart/joinedEnd`. `wallJoinPatches` удаляется.
4. Каждая грань получает `ref: { type: 'wall', key, face }`, где `face` —
   `'top' | 'side' | 'end'` + нормаль. Сейчас грань несёт только `kind: 'wall'`.

`core/ifc.js` — то же: `IfcWall` на запись, тело — `IfcExtrudedAreaSolid` по
каждому `polys`-контуру (или `IfcFacetedBrep` из `rects`), «Стена (стык)»
исчезает; ручная стена — `IfcWallStandardCase` с осью (`Axis` representation),
что Revit читает как полноценную стену с линией привязки. Высота — `z1 − z0`.
Помещения по стенам — `IfcSpace` по `room.poly`.

### 3.2. Выбор (hit-test) в 3D

`ui/view3d.js` рисует сам (WebGL или canvas 2D, своя перспектива). Решение:
**CPU-луч**:

- Из пикселя — луч в мировых координатах (обратная матрица вида уже есть для
  рендера; вынести `screenRay(x, y)`), перевести в оси дома (обратный поворот
  `building.rotation`, `core/building.js`).
- Пересечение луча с осевыми параллелепипедами `rects × [z0, z1]` всех стен
  (slab-тест AABB), ближайшее попадание → `{ key, face, point }`. Пара тысяч
  коробок — < 1 мс, ускорение не нужно. Проёмы (пустоты) учитываются проверкой
  попадания в `openingRect × [sill, sill+height]`.
- Модуль `core/pick3d.js` (без DOM, тестируется unit-тестом), вызывается из
  `ui/view3d.js`. ID-буфер в WebGL не делаем: не работает в canvas-2D-режиме и
  требует второго прохода рендера.
- Выделение в 3D и на плане — общее (`state.selection`), подсветка граней
  выбранного `key`.

### 3.3. Редактирование в 3D и обратная запись

Ручки (рисуются поверх, как предметы мебели на плане) на выбранной стене:

| Ручка | Жест | Запись в модель |
|---|---|---|
| верхняя грань | тянуть вверх/вниз (проекция на вертикаль через точку попадания) | `setWallHeight(project, key, { top })` → `wallOverrides[key].top` или `wall.top` |
| боковая грань | тянуть по нормали (проекция на горизонтальную плоскость `z = точка попадания`) | комнатная: `moveWallBy` (`core/wall-edit.js`); ручная: `moveManualWall` |
| боковая грань + Alt | толщина, противоположная грань на месте | `setSharedWallThickness`/`setWallKind` (`core/wall-thickness.js`) или `setManualWallThickness` |
| торец (ручная) | тянуть вдоль оси | `dragManualWallEnd` |
| число | двойной клик по ручке → ввод (как `ui/dim-input.js`) | то же |

- Все жесты идут через те же функции, что и в плане, и той же транзакцией
  `store` (одна запись в историю на `finalize`, без промежуточных — как
  перетаскивание стены в плане).
- Во время перетаскивания: правка модели → `deriveWallsV2` → пересборка меша.
  Полная `buildHouseMesh` сейчас — весь дом с крышей/участком; для кадра
  перетаскивания пересобирать только слой стен и плит этажа (`buildLevelWalls`
  выделить из `buildHouseMesh`), остальное — из кеша. Цель — ≤ 16 мс на шаблонах.
- Снапы в 3D: шаг сетки `GRID_STEP`, совпадение с гранями соседей
  (`core/draw-snap.js`) — переиспользовать в осях дома по проекции.
- На телефоне (`ui/mobile.js`) — только выбор и ввод числа, без перетаскивания граней
  (касание слишком неточное по глубине).

## 5. Решение: перекрывающиеся комнаты

Варианты:
1. **Ошибка планировки (выбрано).** Стены внутри чужого `P_s` не рисуются
   (естественное поведение `Ring_r \ P_s`). `core/norms.js` — ошибка «Помещения
   «А» и «Б» перекрываются (N м²)», подсветка зоны пересечения на плане,
   действие «Обрезать «Б» по «А»» (контур через `outline`). Площади в ТЭП
   считаются по объединению, чтобы не было двойного счёта.
2. Перегородка на участке внутри чужой комнаты (старое `covered`). Отклонено:
   это единственная заплатка, которая создаёт стену там, где её не задавал ни
   контур, ни пользователь; она же даёт дефекты e/c на узлах.
3. Запрет перекрытия при перетаскивании. Отклонено: `validateRoomPlacement`
   (`core/rooms.js`) уже не даёт создать перекрытие обычным жестом; жёсткий
   запрет мешает промежуточным состояниям при правке контура и импорту.

Почему безопасно: в реальном проекте пользователя перекрытий 0; вложенные
(`parentId`) и шахты — не перекрытие (они в `Anc(r)`), их поведение
сохраняется. Нужна стена в зоне перекрытия — рисуется ручной стеной (теперь это
возможно). Тест: фикстура `overlapPair` — ровно одно предупреждение норм, нет
стен внутри обеих `P`, инварианты a–f зелёные.
